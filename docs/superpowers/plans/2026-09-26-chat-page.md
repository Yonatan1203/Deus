# Chat Page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Chat tab becomes a WhatsApp-style conversation with Amos in the Claude-app look. It follows the mockup the operator saw on 2026-09-26 (`docs/control-ui/artifacts/chat-mockup.png`, sample content only):
- a chat list, with chats saved on the server so phone and PC match;
- Amos's slash commands;
- a model picker and an effort picker for Amos's turns.

**Architecture:**
- Chats live in `<configDir>/control-ui/chats/<id>.json`, one file per chat.
- A chat turn names its chat; the server builds the history from the saved chat, not from the browser.
- The server saves the reply when the turn ends, even if the browser has gone away. A phone that locks mid-reply still gets the answer.
- Model and effort go per chat, through the existing web-turn → container path. A new `model` field travels next to the existing `effort` field.
- The Claude tab's message box (the `/` menu, pickers and autosize) becomes a shared `web/control/composer.js`, used by both tabs.

**Tech Stack:** Node/TypeScript host, the container agent-runner (Claude Agent SDK), vanilla ES modules, vitest.

**Spec:** the operator's Chat requests in this session. The two decisions are "Save on server" and "Add agent opens the Claude tab"; the latter is planned separately.

## Global Constraints

- Security brief:
  - Loopback only.
  - Nothing that renders keys, tokens or channel auth state.
  - Destructive actions need typed confirmation. Deleting a chat is one.
  - Container isolation and mounts are unchanged.
  - Anything touched outside the checkout is backed up.
- Chat files: mode 0600 in a 0700 directory, written atomically (temp + rename). They are never symlinked or read outside that directory; the id must match `^[0-9a-f]{16}$`.
- Every string the UI draws goes through `h()` or the markdown renderer (no HTML).
- `model` is only ever one of a fixed allowlist, checked on the host (route and `ContainerInputSchema`) and again in the runner. `effort` keeps its existing enum.
- No user data is dropped silently:
  - A full chat refuses new messages and says so.
  - Chat history the browser kept locally today is imported once, and the local copy is cleared only when every message was imported.

- No model is passed today. Container turns log `model_usage` for `claude-sonnet-4-6`, the SDK default: 63 of 63 in `logs/deus.log`.
- Amos's commands are the container skills in `container/skills/*/SKILL.md`: agent-browser, capabilities, compress, preserve, resume and status.

### Task 1: Chat store

```ts
export interface ChatMessage { role: 'user' | 'assistant'; text: string; at: number; activity?: string[]; error?: string }
export interface Chat { id: string; title: string; created: number; updated: number; model: AgentModel | null; effort: AgentEffortLevel | null; running_turn_id: string | null; messages: ChatMessage[] }
export interface ChatSummary { id: string; title: string; updated: number; preview: string; model: AgentModel | null; effort: AgentEffortLevel | null }
export function createChatStore(dir: string, now?: () => number): {
  list(): ChatSummary[];                      // newest first
  get(id: string): Chat | null;
  create(init?: { title?: string; messages?: ChatMessage[] }): Chat | { error: string };
  update(id: string, patch: { title?: string; model?: AgentModel | null; effort?: AgentEffortLevel | null }): Chat | null;
  append(id: string, m: ChatMessage): Chat | { error: string };
  remove(id: string): boolean;
};
```

Caps and rules, each tested:

- At most 50 chats. Creating a 51st returns `{ error: 'too many chats — delete one first' }`.
- At most 400 messages per chat **and** at most 4 MiB serialized. `append`/`create` compute the size the file would have and refuse past either limit with `{ error: 'this chat is full — start a new chat' }`. The read cap is 5 MiB, above the write cap, so a saved chat can always be read. Both boundaries are tested (under 400 messages but over 4 MiB; exactly at the limit).
- Text is at most 32 KiB. Activity is at most 30 lines of 200 characters each. A title is at most 80 characters, and defaults to the first user message's first line.
- The directory is created 0700, and each file is written 0600 through a temp file and a rename.
- Ids come from `crypto.randomBytes(8)`. `get`/`remove` refuse any id that doesn't match the pattern, and refuse symlinks. A file that fails to parse or is larger than 5 MiB (the read cap) is skipped in `list` and returns null from `get`; it is never overwritten.
- `create` with `messages` (the one-time import) validates each entry the same way `append` does.
- A chat may carry `running_turn_id: string | null`, set when a turn starts and cleared when it ends. `setRunning(id, turnId | null)` does this.
- `interruptStale()` runs once at startup, called from `createControlServer()` in `server.ts` right after the store is created and before the first request is served. For each chat still marked running, it appends `{ role: 'assistant', text: '', error: 'Interrupted — the service restarted before Amos replied.' }` and clears the marker, so a restart never leaves a silent gap.
- `append`/`setRunning` on a chat that has been deleted are no-ops. They never create the file again.

- [ ] Tests: file safety. That covers the id pattern, a symlink refused, a corrupt or oversized file skipped and never overwritten, 0600/0700 modes, and the temp-and-rename write (`wx`).

### Task 3: Chat routes

- `GET /api/v1/chats` returns `{ chats: ChatSummary[] }`.
- `POST /api/v1/chats` (`{ title? }` or the import form `{ title, messages }`) returns the new chat.
- `GET /api/v1/chats/:id` returns the chat.
- `PATCH /api/v1/chats/:id` changes `{ title?, model?, effort? }`; `model`/`effort` may also be `null`, which means Amos's default.
- `DELETE /api/v1/chats/:id` needs `X-Confirm: <id>`; the UI asks the operator to type `delete`.
- `POST /api/v1/chat/turns` with `{ chat_id, message }`:
  - Loads the chat.
  - Appends the user message and broadcasts `chat`.
  - Builds the prompt from the saved messages' `text` only (never `activity` or `error`), up to 200 messages **and** 256 KiB in total. Selection walks backward from the newest message until either limit is hit. The selected window is then passed to `buildConversationPrompt()` in chronological order (oldest first), which that function requires: it finds the live user ask by scanning back from the end (`src/odysseus-server.ts:184-214`). Oldest messages beyond the window are left out of the prompt but stay in the chat. A test checks the order and that the new user message is last.
  - Sets `running_turn_id` on the chat, and clears it when the turn ends.
  - Runs with the chat's model and effort.
  - Streams as today and collects `output_text` and `activity` on the server.
  - When the turn ends, appends the reply (or `{ error }` when there is no text) and broadcasts `chat`.
  - A closing response no longer aborts the turn. `DELETE /api/v1/chat/turns/:id` still stops it.
  - `chat_id` is required. The old browser-supplied `history` path is removed, because it allowed a `system` role and is a second, weaker way to build the prompt. An old cached page gets `400 'chat_id is required — refresh the page'`. The service-worker bump makes that rare.
- `GET /api/v1/chats/:id` includes `running_turn_id`, so a reopened phone or PC can show the typing row and stop the turn with `DELETE /api/v1/chat/turns/:id`.
- `GET /api/v1/chat/commands` returns `{ commands: readSkillDir('<repoRoot>/container/skills', 'amos'), models: <true when the control group's backend is claude> }`.
- The import form of `POST /api/v1/chats` has an explicit `maxBody` of 1 MiB. Trimming is the browser's job (a body over the limit is refused before it is read). The browser records its full local count before trimming (`localTotal`), sends the newest messages that fit, and the response says `{ imported: N }`. The browser clears its local copy only when N equals `localTotal`. Any non-success response (for example a 400 because the import exceeds the 400-message cap) counts as `imported: 0`: the local copy is kept. When fewer were imported, it shows "Imported the newest N of M messages — the older ones are still kept in this browser" and keeps the local copy, so nothing is lost silently. Tested with a cut-down import.
- The `chat` hub broadcast carries `{ id, action }` only, never text.
- Read-only mode may list and read chats. Every write refuses (403), as the router does today for mutations.
- Rate limits:
  - The existing chat-turn admission (one turn in flight).
  - Chat CRUD shares one limiter of 60 per minute per login.
- Audit: `control_ui_chat_*` events with the chat id and never the content. The chat-turn log line carries `chat_id` next to the existing `turnNonce`.
- Tests cover each route: happy path, bad id, caps, read-only, confirmation. One test checks that a reply is saved after the response closed early.
- [ ] Route tests: list/create/get/patch/delete, including the bad id, `X-Confirm`, read-only 403 and the CRUD limiter.
- [ ] Turn tests:
  - `chat_id` is required.
  - The user message is saved at once.
  - The reply is saved after the response closed early.
  - The prompt holds only `text`, within 200 messages and 256 KiB.
  - `running_turn_id` is set and cleared.
  - A chat deleted mid-turn is not recreated.

### Task 5: Chat UI

- The layout is a chat list plus the open chat, like the Claude tab. On a phone, the list is its own screen and a chat opens full-screen with a back button.
- The list has **New chat** at the top and each chat's title, preview and time, grouped Today / Earlier. It refreshes on the `chat` hub event.
- The header has Amos's name and a status dot, plus **Rename** and **Delete** (typed `delete`).
- Messages:
  - Your messages are right-hand bubbles with the time.
  - Amos's replies show an avatar with markdown text (`markdown.js`), a fold "Worked through N steps ›" listing the activity lines, and the time.
  - Days are separated.
  - Errors show as a quiet line.
- While a turn runs:
  - A typing row shows the latest activity line.
  - Text streams in.
  - Send becomes Stop.
- The composer is shared:
  - The `/` menu lists Amos's commands.
  - The footer reads "Amos".
  - Model pill: Default, Opus 5.5, Sonnet 5 or Haiku 4.5.
  - Effort pill: Default (Amos's own), Low, Medium, High or Max.
  - Picks are saved on the chat with `PATCH`; the menu note says "Only for this chat".
- Import: the first time, if `localStorage` still holds `deus_ctl_chat` with messages, create a chat "Earlier chat" from them. Before trimming to fit under 1 MiB, the browser records `localTotal = local.length`. It clears the local copy only when the server's `imported` equals `localTotal`, the full count, not the count it sent. Otherwise it keeps the local copy and shows the "newest N of M" note once, with M = `localTotal`. After any import it sets `deus_ctl_chat_imported=<chat id>` in `localStorage`, and never imports again while that flag is set. That flag is part of the "import happens once" check below.
