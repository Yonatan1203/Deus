# Browser agent, part 1 — control plane (Phase E1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Everything the browser agent needs except the browser: the closed site and action tables, the operator's rules and budgets, the job queue with its approvals and audit, the two site adapters written and tested against local fixtures, the CLIs a session uses, and the dashboard tab — shipped whole, reviewed, and unable to touch a live account.

**Why this is half a phase, on purpose.** The original Phase E plan carried both the control plane and the privileged execution model (a second uid, a Chromium sandbox, a relocated tree, an installed runner, a setup script). Three threat-model rounds converged on the control plane and did not converge on the execution model: each fix to it moved the problem rather than closing it, ending at the finding that the runner's own code sits under `/root` (0700) where a lower-uid child cannot load it. That is the round-count re-scope checkpoint in `plan-review-rules.md`. The disputed component is split out as **Phase E2** (scoped at the end of this document); everything the three rounds *did* converge on ships here.

**What E1 deliberately cannot do:** it never launches a browser on any production path (the adapter tests launch one against local fixture HTML, which is how the adapters are tested at all), and **it never stores a session credential** — a logged-in cookie on disk with nothing able to use it is risk without benefit, so session upload, the profile directory and the whole credential surface move to E2 with the execution model. Approving a job in E1 records the approval and marks the job `blocked: 'sandbox-unavailable'`, and the tab says which phase enables execution.

**Architecture:** one registry family under `CONFIG_DIR/browser/` (root-owned, the same reachable location as every other registry in this dashboard — the relocation to `BROWSER_DIR` belongs with the second uid in E2): `rules/<site>.json`, one file per job at `jobs/<id>.json`, and `attention/<site>`. Reads use the Phase W confinement (`readRecordFile`, `O_NOFOLLOW`, size bound, fresh literal, closed reason enum); writes use the Phase A shape (`wx` temp + rename, `rev` re-check) under a lock whose filename is a parameter. The dashboard's Browser tab shows rules, today's and this week's counts, the approvals queue and the run log, fed by `createDirWatcher` on the jobs dir.

**Tech Stack:** Node `fs` (confined), Playwright 1.62 *as a type and test dependency only* (adapters take a `page`; only the tests construct one), vitest with local HTTP fixtures, vanilla ES modules with `h()`.

**Spec:** `docs/superpowers/specs/2026-09-21-browser-agent-design.md` — **not yet tracked**; Task 3 commits it there, as every prior phase did with its own spec. Until then the only copy is job-local.

**Review gates:** plan-reviewer and threat-modeler on this document before code (this is the settled artifact both see); `oracle-author` writes the blind red test for the caps/allow-list/approval contract before Task 1's implementation; code-reviewer and verification-gate before the commit.

**Prior decisions this plan is bound by** (vault, 2026-09-18, `Atoms/decision-newlybaby-social-follow-plan-google.md`, `methodology-newlybaby-social-follow-warmup-budgets.md`): the follow list and its budgets already exist in the operator's "newlybaby — Social Follow Plan" sheet — **weekly** numbers (Instagram 25/week rising to 30, TikTok 15→20), chosen "below community-reported daily limits to avoid account suppression" — and the recorded decision is "founders tick ✓ manually; Deus only adds on request". Two consequences, the second a departure that is named rather than buried:

1. The default path — the assistant proposes, the operator approves each action — keeps **who decides** exactly where the recorded decision put it. It does move **who acts**: the founder ticked the follow themselves; from E2 on, the assistant's browser performs the click and the founder authorises it. That is a real change in the operator's risk (an automated click is what platforms detect, not a human one) and it is named here rather than smuggled in under "one approval at a time".
2. `autonomous: true` is a **deliberate extension beyond it**: once the operator types the site name to enable it, follows inside the caps run with no per-action tick. Offered because the scope is narrow (one kind; targets that must already be on the operator's allow-list; weekly and daily caps from the sheet; pacing; quiet hours; stop on any challenge), off by default, never available to `alibaba.*`. When the operator first enables it, the vault record should be superseded with a note — flagged here, not written, because the assistant does not edit the operator's memory unasked.

The sheet stays the source of truth and nothing in this phase writes to it.

## Global Constraints

- **Sites and actions are closed tables in code**, never operator input: `instagram` and `alibaba`; kinds `instagram.follow { handle: /^@?[A-Za-z0-9._]{1,30}$/ }`, `alibaba.reply { thread_id: /^[A-Za-z0-9_-]{1,64}$/, body: 1..2000 }`, `alibaba.list_threads {}`. `:site` is matched against the table before anything is joined to a path. **A job carries validated parameters and nothing else** — never a selector, a URL, or code. `src/browser/sites.ts` is a closed in-code registry rather than a data file precisely because each site needs an adapter, which is code.
- **Rules are data, never code.** `CONFIG_DIR/browser/rules/<site>.json`: `{ v: 1, site, enabled, autonomous, weekly_cap: 1..500, daily_cap: 1..200, min_gap_seconds: 15..3600, jitter_seconds: 0..600, quiet_hours: [startHour, endHour] | null, allow: { kinds: [closed enum], handles: [≤500 × ≤64 chars], threads: [≤500 ids] } }`. Validated on read into a **fresh literal** with a closed reason enum (`unreadable | too-large | not-json | bad-schema`), and `record.site` must equal the filename's site the way a job's `id` must equal its own — so a confirmed record cannot be transplanted into another site's path and still verify; an invalid file **disables** the site rather than defaulting to permissive; a missing file reads as `{ enabled: false }`, not an error.
- **Autonomy cannot be granted by writing a file.** `autonomous: true` is honoured only when the same record carries **both** `autonomy_confirmed_at` **and** `autonomy_scope_sha256` — a hash over **the whole validated record except the two confirmation fields themselves**, rather than an enumerated subset, so nothing that widens autonomy can be forgotten now or added later: `enabled` (autonomy is inert while a site is paused, so a pause takes effect immediately rather than waiting on a re-confirmation), `site`, and every field E2 adds to this record are covered by construction — **corrected 2026-09-22**: this sentence originally claimed coverage stops a site being paused and flipped back at full confirmed scope. It cannot: flipping `enabled` back restores the scope bytes exactly, so the hash matches again whether or not `enabled` is inside it. What stops that in practice is that every writer here destroys the confirmation, leaving only a raw hand-edit — recorded as a named residual in `docs/KNOWN_LIMITATIONS.md` and in `docs/decisions/browser-autonomy-confirmation-hashing.md` — and **`PUT /api/v1/browser/sites/:site/rules` is the only writer of either field**, the route that already demands the typed site name. `validateRules` recomputes the hash on every read and, on mismatch, reads `autonomous: false`. Confirming the grant without binding its scope would have moved the hole rather than closed it: one confirmation at the sheet's 25/week over the operator's own handles, and any later writer at this uid could widen the caps to 500 and swap in its own list while keeping the confirmation. A cap or allow-list edit made outside the dashboard therefore costs one re-confirmation in it — which is the point. `scripts/browser-rules.mjs set` additionally **drops both fields** on every write, so the CLI cannot even carry a stale confirmation forward. `validateRules` reads `autonomous: true` without it as `autonomous: false`, the same fail-closed posture as an invalid file. This matters because the rules file is writable by any host session at this uid: without it, a session could hand itself `autonomous: true` with its own allow-list and caps, and the poller would then approve its own proposals with no operator tick — the exact content-driven mistake this phase exists to stop, defeated through the back door. Stated honestly: this closes the mistake, not a compromised same-uid session, which nothing at one uid can close.
- **The target lists are enforced, not decorative.** Every job's params must be members of the list its kind draws on (`instagram.follow` → `handles`, `alibaba.*` → `threads`), compared after the normalisation the params regex already allows (a leading `@` and case are ignored for handles). `autonomous: true` with an empty or missing target list for an allowed kind is **invalid rules**, not permission for anything.
- **The operator's budgets are weekly, so the rules are too.** `weekly_cap` is the number copied from the sheet; `daily_cap` is how far it may be spread in one day — the CLI and the editor default it to `ceil(weekly_cap / 7)` and refuse a value above `weekly_cap`. Both bind. Copying a weekly figure into a daily field would have allowed roughly seven times the intended volume, the exact opposite of the sheet's stated reason for those numbers.
- **Counting is exact or it refuses.** The caps are counted by a dedicated pass — the same mtime-descending walk of `jobs/`, stopped at the Monday boundary — and **not** from the list the UI reads. That list carries the Phase W bound (newest 600 parsed, 200 returned, and an empty result with `too-many` past the scan cap, `workflows.ts:310-337`), and counting from it would fail *open*: a truncated list reads as headroom, and Phase W's ranking drops terminal records first — exactly the `done` jobs the caps exist to count. The counter returns `{ counts, exact }`, and `capCheck` refuses with the closed reason `counts-unavailable` whenever `exact` is false. **`exact` is false on any doubt at all**: the scan cap, of course, but equally a record inside the counted window that fails to read (`readRecordFile` returns `unreadable | too-large | not-json`, `workflows.ts:182-184`) or an entry that vanishes between `readdir` and `stat` (swallowed at `workflows.ts:302`). Tolerating a corrupt record is right for the queue — that is why jobs are one file each — and is exactly the wrong thing for the counter: there, a skipped record is a missing action. Membership in the window is decided by the record's own `finished_at`/`started_at`; mtime is used only as the descending-walk stop, and the walk continues **48 h past** the Monday boundary before stopping so ordinary mtime skew cannot truncate the window. An undercount must never look like room.
- **`capCheck(rules, job, counts, now, random)`** — one function the approve route and (in E2) the runner both call — refuses with a closed `RefuseReason` (`disabled | quiet-hours | daily-cap | weekly-cap | too-soon | not-allowed | rules-invalid | needs-attention | expired | counts-unavailable`) unless: `enabled`; the job's params are on the allow-list; the clock is outside `quiet_hours` (a window that wraps midnight is handled); `done + running + maybe-sent` for that site **since local midnight** `< daily_cap` **and since the most recent local Monday 00:00** `< weekly_cap` — *local* meaning the timezone the service process runs in (the unit's `TZ`; this instance sets `TIMEZONE=Europe/Rome`), computed with `Date` so a DST shift moves the boundary with the operator's own clock rather than drifting an hour away from the sheet they read; and the last action for that site finished at least `min_gap_seconds + random(0..jitter_seconds)` ago. `maybe-sent` counts in both totals and in the gap — an action nobody can prove did not happen must not be free. `failed` and `blocked` do not count.
- **A job record** is `{ v: 1, id: /^bj-[0-9a-f]{12}$/, site, kind, params, status, proposed_by, proposed_at, approved_by?, approved_at?, rules_mtime?, started_at?, finished_at?, result?, reason?, shot?, rev }`. Status: `proposed | approved | running | done | failed | maybe-sent | blocked | rejected | expired`. **String enums in this phase follow the subsystem's existing convention — hyphens** (`workflows.ts:37-45` already uses `bad-schema | too-large | not-json | too-many`, and `readRecordFile` returns exactly those), so the registry reasons this phase reuses and the reasons it introduces read the same way. Field names stay snake_case, as in every other registry here. Validated like every other registry here, including `record.id === basename(file, '.json')`. **A proposal older than 24 h is expired at read time**, not by a background transition: `listJobs`/`readJob` project a `proposed` record whose `proposed_at` is over 24 h old as `expired` (nothing is rewritten), `capCheck` refuses it with reason `expired` so both the approve route and E2's runner see the same answer, and a sweep prunes them once they are a week old. **Terminal records are pruned too** — `done`, `failed`, `blocked`, `rejected` and `maybe-sent` older than 30 days — because without that they accumulate until the directory passes the scan cap and the counter goes permanently `counts-unavailable`, which would brick the approve route rather than merely autonomy. That is reachable sooner than the arithmetic suggests: `browser-job.mjs propose` writes files directly and is behind no HTTP limiter, so one looping session is exactly the content-driven mistake this phase exists to survive. The sweep is the documented exit; the operator never has to `rm` inside `CONFIG_DIR`. **That sweep is owned by the server's own timer** (the same shape as the other periodic work, on its own interval rather than hanging off a request) and it **never runs on the read-only path**: a deletion triggered by a read-only client listing jobs would cross this phase's own rule that read-only refuses every mutation.
- **Approval is a workflow control, not a privilege boundary — and this plan says so.** The control server, the two `scripts/browser-*.mjs` CLIs — `browser-job.mjs`, which a session runs, and `browser-rules.mjs`, which is an operator tool — and `CONFIG_DIR/browser/**` all share one uid; a host session that is already compromised can write a job file or rewrite `rules.json` without touching the API, and no code here prevents that. What the gate protects against is the realistic case: **content-driven mistakes**, a session proposing the action a supplier's message asked for. Against that: `POST /jobs` sets `status: 'proposed'`, `proposed_at` and `proposed_by` itself and ignores all three in the body — `proposed_by` is a closed provenance value, `session:<shortId>` from the authenticated session or `cli` from a file-written proposal, **rendered distinctly in the approve queue** because the queue is where the operator's read happens and attribution they cannot trust is worse than none; it is carried on the `_job_proposed` audit line too. `proposed_at` written by the CLI path is **clamped to `min(value, now)`** by `validateJob`, so a future timestamp cannot postpone the 24 h expiry; a job file written outside the API — by `browser-job.mjs` or by a raw write mimicking it — can carry no status but `proposed`, because the runner and the approve route both re-derive status from their own checks rather than trusting the record (`browser-rules.mjs` writes rules, not jobs, and is bounded instead by being unable to write either autonomy field); and every approval re-runs `capCheck` against the rules on disk at approval time, recording `rules_mtime` **and `rules_sha256`** (mtime is settable with `utimes` at this uid and is the weakest of the three bindings), the job `rev` it approved (`approved_rev`) and a `params_sha256`. Binding the approval to the rules version but not to the content version would leave the params rewritable after the tick; E2's runner re-checks both before acting. No body ever enters a log — only its hash.
- **Approval shows the words.** The approve dialog for `alibaba.reply` renders the **full body** it would send (text nodes, as everywhere) above the typed confirmation — when a session drafted that text from a supplier's own message, the operator's read is the only control on it. `alibaba.reply` and `alibaba.list_threads` **never** auto-approve, even with `autonomous: true`: sending words in the operator's name is not a rate-limited action, and reading an inbox is not one either.
- **Auto-approval is bounded and attributed.** The poller (30 s, only while a dashboard client is connected) approves at most one job per tick per site, only when `rules.autonomous`, only for `instagram.follow`, only inside `capCheck`, and records `approved_by: 'rules'` with `rules_mtime`.
- **Stop-on-challenge is already here, even though nothing runs yet — and it is scoped so it cannot fire on a fact about this phase.** Only outcomes that came back **from a site** raise `attention/<site>`: the adapter reasons `challenge`, `signed-out`, `rate-limited`, `not-found`, `changed-page` (all of which arrive in E2, since E1 never runs an adapter outside tests). `sandbox-unavailable` — which in E1 is the outcome of *every* approval, because execution is refused by construction — explicitly does **not** raise it, and neither do the cap refusals. Reading it the other way would have been self-defeating: the first approval would have raised the banner and stopped the poller for a condition that is not a problem, and the autonomous path could never have been demonstrated. While the marker is set while it is set the poller approves nothing for that site and the tab shows a banner. Clearing it needs the typed site name.
- **Execution is refused by construction.** `POST /jobs/:id/approve` records the approval, then marks the job `blocked: 'sandbox-unavailable'` with the message naming Phase E2 — E1 contains no production code path that spawns a process or opens a browser (the adapter tests open one against local fixture HTML), and two tests keep it that way: one asserts the approve route performs no spawn (an injected spawn spy that must never be called), and one asserts **`playwright` appears in `devDependencies` and not in `dependencies`** — a production install of E1 has no launcher at all. That invariant is exactly what E2 flips, deliberately and under its own review. **No session credential is accepted or stored in E1**; the session store, the profile directory, the runner and its setup belong to E2.
- **Adapters are pure over a page.** `src/browser/adapters/*` export `{ id, actions: { [kind]: (page, params) => Promise<AdapterResult> } }` with `AdapterResult = { ok: true, detail? } | { ok: false, reason: BlockedReason }` and `BlockedReason = 'challenge' | 'signed-out' | 'rate-limited' | 'not-found' | 'changed-page'` — the five things a *site* can tell us, distinct from `capCheck`'s `RefuseReason` (what our own rules say) and from the job status `blocked: 'sandbox-unavailable'` (a fact about this phase) — **Strategy**, one adapter per site behind one interface, selected by the closed `SITES` table, so the engine holds no site knowledge and a new site is one file plus one row. **Adapters never navigate.** The engine puts the page on the right URL — built from the closed `SITES` table plus validated params, never from anything an adapter or a job supplies — and the adapter acts on the page it is given. That keeps "never leaves the site" structural rather than a promise, and it means the fixture tests need no retargeting seam: the test drives `page.goto(fixtureUrl)` itself and hands over a page already on the fixture. E2 inherits an interface with no URL in it. Adapters also never read files, never log and never construct a context. In E1 only tests call them.
- **Audit everything that changes state**: `control_ui_browser_rules_saved` (site, enabled, autonomous, weekly_cap, daily_cap), `_job_proposed` (site, kind), `_job_approved` (id, site, kind, `auto: true|false`), `_job_rejected`, `_job_blocked` (id, reason), `_attention_cleared`. No message body and no handle beyond what the operator already sees in the queue.
- **Read-only** refuses every mutation (403); the list still answers, through **one `projectJob(job, { readOnly })` used by both the REST list and the SSE frame**, so `params` and `result` are withheld on both paths.
- Public-repo generic: fixtures are local HTML with invented handles and thread ids; captures use them; no real account, credential or list appears in the repo.
- Visual language: the existing tokens, `header()`, `.card`, `.badge`, the Workflows grid.

## Design

- `src/browser/sites.ts` — `SITES` (id, baseUrl, requestHosts, cookieDomains for E2), `getSite(id)` and **`urlFor(kind, params)`**, which builds every URL the engine will ever navigate to from the closed table plus validated params, with explicit per-segment encoding and a rejection of handle segments that are dot-only (`.`, `..`): the handle regex admits dots, and a path builder is where that belongs. It builds from **the same normalised handle the allow-list membership test uses** — one normalisation function, used by both — because checking one form and navigating another is how the two quietly diverge. It ships **in E1, with tests**, so the structural claim "adapters never navigate" rests on an artifact here rather than on a promise in E2. No I/O.
- `src/control-ui/api/browser-store.ts` — `validateRules`/`readRules`/`writeRules`, `validateJob`/`readJob`/`listJobs`/`writeJob`, **`countActions(dir, site, now)` → `{ counts: { day, week }, exact }`** — the exact pass described above, and the single source of those numbers: `capCheck` consumes it, and `GET /api/v1/browser` displays it rather than counting separately, so the tab never shows a number the enforcement path would refuse to trust (and renders "counts unavailable" when `exact` is false). `capCheck` (which owns `expired`; `sandbox-unavailable` is **not** one of its reasons — the approve route sets that status itself, after `capCheck` has already passed, because it is a fact about this phase rather than a judgement about the job), `attention()` get/set/clear, `projectJob`. `listJobs` carries the Phase W enumeration bound (`candidatesMax`, and `reason: 'too-many'` past the scan cap, `workflows.ts:334,337`) because the SSE watcher re-reads this directory on every debounced tick; **`expired` records are pruned, not merely labelled**, by the same sweep. Reads via `readRecordFile(file, 64 KB)`; the dir is `lstat`-guarded; writes use the Phase A `wx` temp + rename + `rev` re-check under `withLock(dir, lockName, fn)` — **`withLock` gains the lock filename as a parameter** (today it hardcodes `${REGISTRY_FILE}.lock`, `artifacts.ts:213`, which would drop an `artifacts.json.lock` into a browser dir and serialise unrelated writes).
- `src/browser/adapters/{instagram,alibaba}.ts` — the selectors for each site in one `SELECTORS` object per adapter, so a site change is one line.
- `src/control-ui/server.ts` — `GET /api/v1/browser` (sites, rules, today/this-week counts, attention, `execution: 'unavailable'`), `PUT …/sites/:site/rules` (typed site to enable autonomy), `POST …/sites/:site/attention/clear` (typed site), `GET …/jobs`, `POST …/jobs`, `POST …/jobs/:id/approve` (typed id), `POST …/jobs/:id/reject`. The **auto-approve poller lives in `server.ts` beside the existing ones** and copies their shape exactly — a `setInterval` that returns early while `hub.clientCount() === 0`, `unref()`ed, cleared on close — **`claudePoll` (`server.ts:2111-2133`) is the precedent; `queuePoll` (`:2137-2145`) is not**, since it gates on `deps.runtime` rather than on a connected client, and copying it would produce an auto-approver that runs with nobody at the console. Limiters: reads 60/min, mutations 12/min per session. A `browser` SSE frame from `createDirWatcher` on the jobs dir.
- `scripts/browser-job.mjs` (`propose --site --kind [--handle|--thread|--body]`, `list`, `show`) — **the session-facing CLI**, documented in `AGENTS.md` § Browser jobs; it writes `status: 'proposed'` and nothing else, and cannot touch rules.
- `scripts/browser-rules.mjs` (`set --site --file`, `show`) — **an operator tool, deliberately not in the AGENTS.md section**: everything documented there is an instruction the assistant executes (see `workflow.mjs` at `AGENTS.md:239` and `artifact-registry.mjs` at `:258`), and rules are the thing that bounds the assistant. `set` can write caps and allow-lists; it cannot make `autonomous` effective, because it does not write `autonomy_confirmed_at`. `show` is safe for anyone.
- `web/control/views/browser.js` — per-site card (rules summary, today N/daily and week N/weekly, autonomy chip, attention banner with typed clear, an "execution arrives in E2" note), the approvals queue (kind, params, body-in-dialog for replies, Approve typed by id / Reject) and the run log. Text nodes only.

## Verification strategy (frozen)

| Surface | Predicted |
|---|---|
| Rules | `validateRules` returns a fresh literal and rejects `daily_cap: 0`, `daily_cap > weekly_cap`, `weekly_cap: 501`, an unknown kind, a 600-entry handle list, a non-array `quiet_hours`; an invalid file reads as `{ enabled: false, invalid: true, reason }`; `autonomous: true` with `kinds: ['follow']` and an **empty** `handles` reads as invalid, not as permission; **`autonomous: true` without `autonomy_confirmed_at` reads as `autonomous: false`** (the discriminating case: a rules file written by hand cannot grant autonomy), the same record with both confirmation fields intact reads as `true`, and — the second discriminating case — **a record whose caps or `allow` were edited after confirmation, keeping `autonomy_confirmed_at` and its old `autonomy_scope_sha256`, reads as `autonomous: false`**; `browser-rules.mjs set` writes neither field even when its input file contains them; the CLI defaults `daily_cap` to `ceil(weekly/7)` |
| Caps | the counter is exact or says so: with 5 000 job files it returns `exact: false` and `capCheck` refuses with `counts-unavailable` (the approve route answers 409, never 200) — asserted against a fixture directory past the scan cap, and against a directory where the newest 600 are all `proposed` while older `done` records carry the real count; `capCheck` refuses on `disabled`; inside `quiet_hours` including a window that wraps midnight (fake clock); at `daily_cap`; **at `weekly_cap` with the daily count still low** (a Monday-boundary case); when the last action finished `min_gap_seconds - 1` ago; for a target outside `allow.handles` (`not-allowed`) — and passes just past the gap with `random: () => 0`. A `maybe-sent` job counts toward both totals and the gap; a `failed` one does not |
| URLs | `urlFor` over every kind and every regex-valid param: the built URL's origin always equals `SITES[site].baseUrl`; `.` and `..` handles are rejected; a handle differing only by a leading `@` or by case produces the same URL as the allow-list membership test accepts (one normalisation, asserted on both paths) |

## Phase E2 — what this split defers (its own plan, its own threat rounds)

Everything that makes a job actually run, kept together because the three threat rounds showed these controls only make sense as one artifact. **Cross-checked independently:** the threat review of this E1 document walked the earlier rounds' findings against this section and found all of them traceable here — the `/root` 0700 runner-reachability finding, `ubuntu` as root-equivalent, sandbox-as-capability with no retry, the run uid reading but not writing what bounds it, the handoff nonce written-then-unlinked and read `O_NOFOLLOW`, forget removing both roots with "local deletion is not revocation", the propose-time screenshot dropped rather than deferred, and `maybe-sent` counting in both totals and the gap. The one item it found unowned, `requestHosts`, is now item 4.

1. **A place to run from.** `scripts/browser-setup.sh` (written there, run by the operator) creating a dedicated `deus-browser` account — nologin, no sudoers entry, not in `sudo`/`adm`/`lxd`, because `ubuntu` is `NOPASSWD:ALL` on this host and an escape to it is an escape to root — plus `BROWSER_DIR` (`/var/lib/deus-browser`) holding the profile, shots, handoff **and an installed copy of the compiled runner with its `playwright` dependency**: the checkout is under `/root` (0700), so a lower-uid child cannot load its own entry script from there.
2. **Privilege dropped by the parent**: optional `uid`/`gid` on `createHostCli` → `execFile` (verified: Node clears root's supplementary groups), never an in-child `setuid`.
3. **The sandbox as a capability, not a flag list**: no `chromiumSandbox: false`, no `ignoreDefaultArgs`, no sandbox-disabling argument, asserted over the options the runner builds; any namespace/sandbox launch failure is `blocked: 'sandbox-unavailable'` with no retry — expected first on this host, which has `kernel.apparmor_restrict_unprivileged_userns = 1` and no AppArmor profile for Playwright's Chromium, so an AppArmor profile or a deliberate sysctl decision is the operator step.
4. **Network confinement for the runner's context**: the request filter installed on the **context** (so popups and iframes are covered) aborting every request whose host is outside that site's `requestHosts`, with `serviceWorkers: 'block'` (a worker's fetches bypass `context.route`) and `acceptDownloads: false`. `SITES` carries `requestHosts`/`cookieDomains` in E1 for this; E2 is what enforces them.
5. **An ownership table with a mode and a group per row**, where the run uid can read the job and rules it must re-validate but cannot write them, and a **handoff** file it writes that the parent validates and merges — bound to the run with a per-run nonce the parent writes first and `unlink`s before spawning, read with `O_NOFOLLOW`, so a pre-planted handoff for another job cannot be merged.
6. **The session credential**: upload with cookie-domain binding to the site, 0640 readable by the run uid, the profile seeded once via `addCookies` (+ best-effort `addInitScript`; `storageState` is not a `launchPersistentContext` option), and a **forget that removes both the session and the profile roots** — deleting the state file alone leaves a logged-in browser. Local deletion is not revocation; the tab says so.
7. **Screenshots** (shots as evidence, 7-day retention for `alibaba.*`), the before-shot taken inside the same gated child rather than at propose time, `maybe-sent` on a timeout after `attempted_at`, and the `sandbox-unavailable`-vs-`failed` classification of a spawn that dies for a non-sandbox reason.

## Deviations from the spec

- The spec describes one phase; this is its first half, and the split is explained above. E1 ships no session store and no runner, so the spec's § S (Session) and the screenshot parts of § J land in E2.
- Jobs are one file each (Phase W) rather than one registry file (Phase A): a corrupt job must not hide the queue.
- The propose-time preview screenshot is dropped, not deferred: a before-shot is only meaningful taken inside the same gated child that acts, immediately before acting.
- `alibaba.list_threads` is in the closed kind set with no dashboard button, so a session can enumerate threads through the CLI before drafting a reply.
